## 1. Mengapa Rust Lebih Cepat dari Go

Rust biasanya unggul dalam performa mentah karena beberapa alasan desain.

| Faktor | Rust | Go |
|---|---|---|
| **Manajemen memori** | Ownership & borrowing, dicek saat kompilasi | Garbage collector (GC) saat runtime |
| **Abstraksi** | *Zero-cost abstractions*, generics di-*monomorphize* | Generics dengan sedikit overhead dispatch |
| **Compiler** | LLVM, optimasi agresif (inlining, SIMD) | Compiler lebih sederhana, mengutamakan kecepatan kompilasi |
| **Layout memori** | Kontrol penuh: stack, cache-friendly | Escape analysis sering memindahkan data ke heap |
| **Runtime** | Nyaris tidak ada | Scheduler goroutine + GC |

### Penjelasan singkat

- **Tanpa garbage collector.** Tidak ada jeda GC dan tidak ada overhead pelacakan memori, sehingga latensi lebih konsisten.
- **Zero-cost abstractions.** Iterator, closure, dan generics dikompilasi menjadi kode yang setara dengan versi tulis tangan.
- **Optimasi LLVM.** Hasil kompilasi bisa divektorisasi dan di-inline secara agresif.
- **Kontrol memori.** Mudah menghindari alokasi heap yang tidak perlu.

> **Catatan penting:** Go tetap sangat cepat untuk banyak kasus nyata, terutama layanan jaringan, berkat goroutine yang ringan. Selisih performa paling terasa pada beban kerja yang **berat di CPU**, **sensitif terhadap latensi**, atau **butuh memori ketat**. Harga yang dibayar Rust: kurva belajar lebih curam dan waktu kompilasi lebih lama.

## 2. Apakah AI Membuat Rust Jadi Mudah?

**Sebagian benar.** AI menurunkan hambatan awal, tetapi tidak menghapus kesulitan intinya.

### Yang jadi lebih mudah

- Menulis boilerplate, struktur data, dan kode umum (parsing, CLI, HTTP handler).
- Menerjemahkan pesan error compiler yang panjang dan memberi saran perbaikan.
- Memperbaiki error lifetime atau borrow checker yang sederhana.
- Menjelaskan konsep seperti ownership dan trait sambil Anda belajar.

### Yang tetap sulit

- **Desain.** Menentukan siapa memiliki data, kapan memakai `Rc`/`Arc`, dan bagaimana menyusun struct adalah keputusan arsitektur. AI sering "memaksa" kode lolos kompilasi lewat banyak `clone`, `unwrap`, atau `Arc<Mutex<...>>`, sehingga kode berjalan tetapi tidak idiomatik dan kehilangan keunggulan performa.
- **Review.** Lolos compiler tidak berarti benar secara logika, efisien, atau bebas deadlock.
- **Area kompleks.** Async lanjutan, `unsafe`, generics rumit, dan lifetime berlapis adalah tempat AI lebih sering salah.
- **Waktu kompilasi** tetap lama.

> **Tips:** Minta AI menulis kode, lalu minta ia menjelaskan *kenapa* memilih pendekatan itu. Dengan begitu Anda bisa menilai hasilnya dan belajar sekaligus.

## 3. Memahami `Rc` dan `Arc`

`Rc` dan `Arc` adalah *smart pointer* yang memungkinkan **satu data dimiliki banyak pemilik** (*shared ownership*) lewat *reference counting*.

| | `Rc<T>` | `Arc<T>` |
|---|---|---|
| **Kepanjangan** | Reference Counted | Atomic Reference Counted |
| **Thread** | Satu thread | Aman antar thread |
| **Penghitung** | Biasa (lebih cepat) | Atomik (sedikit lebih lambat) |

Setiap `clone()` hanya menambah penghitung, **bukan menyalin data**. Data dibebaskan saat penghitung mencapai nol.

```rust
use std::rc::Rc;
use std::sync::Arc;
use std::thread;

let a = Rc::new(vec![1, 2, 3]);
let b = Rc::clone(&a); // data tidak disalin, hanya count +1

let data = Arc::new(vec![1, 2, 3]);
let d = Arc::clone(&data);
thread::spawn(move || println!("{:?}", d)).join().unwrap();
```

### Poin penting

- Isinya **immutable** secara default. Untuk mengubah data:
  - `Rc<RefCell<T>>` untuk satu thread.
  - `Arc<Mutex<T>>` atau `Arc<RwLock<T>>` untuk multi-thread.
- Compiler menolak `Rc` lintas thread (tidak `Send`), jadi salah pakai tidak akan lolos diam-diam.
- Hindari **reference cycle** (A menunjuk B, B menunjuk A) karena memori tidak akan dibebaskan. Gunakan `Weak<T>` untuk memutus siklus.

**Aturan praktis:** `Rc` jika single-thread, `Arc` jika multi-thread.

## 4. Saran Paling Krusial

> **Jangan melawan borrow checker. Rancang data Anda agar sejalan dengannya.**

Banyak pemula (dan AI) menganggap error ownership sebagai penghalang yang harus ditembus dengan `clone()`, `Rc<RefCell<...>>`, atau `Arc<Mutex<...>>` di mana-mana. Padahal error itu biasanya **sinyal bahwa desain datanya perlu diubah**.

### Praktiknya

1. **Tentukan siapa pemilik tiap data.** Satu pemilik yang jelas hampir selalu lebih sederhana dan lebih cepat daripada shared ownership.
2. **Pinjam, jangan salin.** Terima `&str` dan `&[T]` sebagai parameter, bukan `String` dan `Vec<T>`, kecuali fungsi memang perlu memiliki datanya.
3. **Pisahkan struct yang dipinjam bersamaan.** Pecah struct, atau simpan indeks/ID alih-alih referensi.
4. **Gunakan tipe untuk menyatakan kondisi.** `enum`, `Option`, dan `Result` membuat keadaan mustahil tidak bisa direpresentasikan.

### Kebiasaan pendukung

- **Tangani error dengan benar.** Hindari `unwrap()` di kode produksi; gunakan `?` dan `Result`.
- **Ukur sebelum mengoptimasi.** Gunakan build `--release` dan profil dulu. Banyak orang menyimpulkan Rust lambat padahal mengukur build debug.

Saat merasa "bertarung" dengan compiler, tanyakan:

> **"Siapa seharusnya pemilik data ini?"**

## 5. Pindah dari Go ke Rust

Gayanya cukup berbeda, tetapi tidak terlalu asing. Keduanya statically typed, menghasilkan binary native, punya tooling bawaan (`cargo` mirip toolchain `go`), dan lebih menyukai struct + method + interface/trait daripada pewarisan kelas. Yang paling berubah adalah **cara berpikir soal memori dan error**.

### Yang perlu dipelajari

| # | Topik | Perbedaan dengan Go |
|---|---|---|
| 1 | **Ownership, borrowing, lifetime** | Lompatan terbesar. Di Go pointer bebas dibagikan karena ada GC; di Rust setiap nilai punya satu pemilik |
| 2 | **Error handling** | `if err != nil` diganti `Result<T, E>` dan operator `?`. Tidak ada `nil`; gantinya `Option<T>` |
| 3 | **Enum & pattern matching** | Enum bisa membawa data, dan `match` memaksa menangani semua kasus. Tidak ada padanannya di Go |
| 4 | **Trait & generics** | Mirip interface, tetapi lebih kuat: ada implementasi default, batasan generic, resolve saat kompilasi |
| 5 | **Immutable by default** | Variabel perlu `mut` untuk bisa diubah |
| 6 | **Konkurensi** | Goroutine/channel diganti `std::thread`, `mpsc`, dan `async/await` (mis. Tokio). Pahami `Send`/`Sync` |
| 7 | **Ekspresi** | `if`/`match` mengembalikan nilai; baris terakhir tanpa `;` adalah nilai return |

### Contoh perbandingan

**Go**

```go
func parse(s string) (int, error) {
    n, err := strconv.Atoi(s)
    if err != nil {
        return 0, err
    }
    return n * 2, nil
}
```

**Rust**

```rust
fn parse(s: &str) -> Result<i32, std::num::ParseIntError> {
    let n: i32 = s.parse()?;
    Ok(n * 2)
}
```

### Kebiasaan Go yang perlu diubah

- Jangan berharap bisa membagikan pointer bebas ke mana-mana.
- Jangan membuat interface besar lebih dulu; untuk kumpulan varian yang tertutup, `enum` sering lebih tepat.
- Siap dengan waktu kompilasi lebih lama dan pesan error panjang (tetapi biasanya sangat informatif).

### Urutan belajar yang disarankan

1. **The Rust Programming Language** ("The Book", gratis), fokus ke bab ownership terlebih dahulu.
2. **Rustlings** untuk latihan kecil.
3. **Proyek kecil**: CLI atau HTTP server sederhana.
4. **Topik lanjutan**: trait lanjutan, async, dan `unsafe`.

## 6. Kesimpulan

- Rust cepat karena **tanpa GC, zero-cost abstractions, optimasi LLVM, dan kontrol memori**, tetapi Go tetap sangat layak untuk banyak kasus.
- **AI membantu** menurunkan hambatan awal, namun **desain dan pemahaman model kepemilikan tetap tanggung jawab Anda**.
- `Rc`/`Arc` adalah alat untuk *shared ownership*, bukan jalan pintas untuk menghindari desain yang baik.
- Prinsip utama: **rancang data agar sejalan dengan borrow checker**, bukan melawannya.
- Latar belakang Go adalah modal bagus: tipe statis, struct, dan konkurensi sudah familiar, jadi fokuslah pada **model kepemilikan memori**.
